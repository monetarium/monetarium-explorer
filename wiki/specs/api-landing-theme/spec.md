# Landing-page theme handoff (требования)

## 0. Контекст

У обозревателя есть тема оформления — светлая или тёмная, — которая хранится в cookie `monetariumDarkBG` **значением**: `1` = тёмная, `0` = светлая (отсутствие cookie = светлая, «выбора ещё не было»; переключатель-солнце в шапке пишет значение на год). Внешняя лендинг-страница monetarium позволяет посетителю выбрать тему до перехода в обозреватель. Задача — чтобы этот выбор «доехал» до обозревателя: если у посетителя ещё нет cookie, тема из лендинга применяется и запоминается; если выбор в обозревателе уже сделан — он не перетирается.

**Зачем.** Лендинг выбирает визуальный тон страницы; разрыв при переходе в обозреватель (светлая страница после тёмного лендинга или наоборот) выглядит как баг и ломает единое впечатление. Механика через URL-параметр не требует cookie с чужого домена и общая с уже существующим механизмом темы.

## 0.1. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Как лендинг передаёт тему | Параметр запроса `?theme=dark` / `?theme=light` к URL обозревателя (§1). Мы диктуем формат ссылки команде лендинга |
| Что происходит, если cookie уже есть | **Cookie выигрывает.** Выбор, сделанный в обозревателе, никогда не перетирается параметром из URL (§3) |
| Что происходит, если cookie нет | Тема из параметра применяется и **сохраняется в cookie** (тёмная — на год, как у переключателя-солнца), чтобы переживать навигацию внутри обозревателя и будущие визиты |
| Светлая тема при отсутствии cookie | Сохраняется **значением** `monetariumDarkBG=0` (§3): явный выбор «светлая» должен отличаться от «выбора ещё не было», иначе следующий `?theme=dark` из лендинга перетрёт его. Пустой cookie ставить нельзя — JS по значению (`=0`) считает светлую |
| Где обрабатывается | Middleware `ThemeFromQueryParser` на web-роутере (Go), до per-route ETag-кэша (§3). Согласованы с ним JS-переключатель и серверный `MenuFormParser` (§2): все пути записи пишут значение, ни один не удаляет cookie |

## 1. Контракт ссылки для лендинга

Лендинг добавляет параметр `theme` к любому URL обозревателя:

```
https://monetarium.online/?theme=dark
https://monetarium.online/address/Tk...?theme=light
https://testnet.monetarium.online/?theme=dark
```

- Допустимые значения: `dark`, `light` (регистронезависимо). Всё прочее игнорируется.
- Параметр безвреден на любой странице: без него и при существующей cookie ничего не происходит.
- Тема не имеет отношения к сетевой теме (`theme-mainnet` / `theme-testnet` — другой механизм, класс на `<body>`, не путать).

## 2. Текущее состояние

| Что | Где |
| --- | --- |
| Cookie темы | `monetariumDarkBG`; имя-константа `darkModeCoookie` (`cmd/dcrdata/internal/explorer/explorermiddleware.go:96`). Значение: `1` = тёмная, `0` = светлая |
| Чтение cookie для шаблона | `commonData` → `Cookies.DarkMode` (`explorerroutes.go:2503`) — истина только при значении `1`; применяется в `extras.tmpl:34,56` (`darkBG` класс, `<meta theme-color>`) |
| Клиентская тема | `public/js/services/theme_service.js` — `darkEnabled()` по **значению** cookie (`=== '1'`); применяет классы на загрузке и на `turbo:before-render`; переключатель-солнце пишет `1`/`0` на год |
| Текущий серверный переключатель | `MenuFormParser` (`explorermiddleware.go:294`) — форма `POST /set`, обратный переключатель, пишет `1`/`0` на год |
| ETag-кэш страниц | `ETagAndLastModifiedIntercept` (`explorermiddleware.go:193`), вешается per-route на кэшируемые страницы |

Чего нет: приёма темы извне (параметра `?theme=`).

## 3. Спецификация поведения

Middleware `ThemeFromQueryParser` (`cmd/dcrdata/internal/explorer/explorermiddleware.go`) монтируется на web-группу обозревателя (`main.go`, `webMux.With(SyncStatusPageIntercept, ThemeFromQueryParser).Group(...)`), до per-route `ETagAndLastModifiedIntercept`.

Логика:

1. `r.Cookie(darkModeCoookie)` присутствует → `next` без изменений. Выбор в обозревателе не перетирается — и тёмный (`=1`), и светлый (`=0`).
2. Иначе читаем `?theme=` (регистронезависимо):
   - `dark` → `http.SetCookie(w, monetariumDarkBG=1; Max-Age=31536000; Path=/)` и `r.AddCookie(тот же cookie)`; затем `next`.
   - `light` → `http.SetCookie(w, monetariumDarkBG=0; Max-Age=31536000; Path=/)` и `r.AddCookie(тот же cookie)`; затем `next`. Светлый выбор сохраняется значением, чтобы не быть перетёртым будущим `?theme=dark`.
   - прочее / отсутствует → `next`.

`r.AddCookie` нужен, чтобы `commonData` для **текущего** запроса уже увидел тёмную тему и отрисовал первый экран тёмным — без этого первый кадр был бы светлым, а JS переключил бы после загрузки (мигание). `Set-Cookie` в ответе дорабатывает браузеру.

Порядок относительно ETag: middleware срабатывает раньше per-route ETag, поэтому `Set-Cookie` пишется даже если ETag-слой ответит `304`; браузер получает cookie, а JS применит тему на загрузке. Случай «закэшированный светлый body + 304» не оставляет посетителя в светлой теме при тёмном выборе.

Граничные случаи:

- Пустой или неизвестный `theme` → ничего не происходит.
- `?theme=dark` при уже тёмной cookie → `next` (cookie существует, шаг 1).
- `?theme=light` при тёмной cookie → `next`, тёмная сохраняется (решение из §0.1).
- `?theme=dark` при светлой cookie (`=0`) → `next`, светлая сохраняется. Это требование ревью: светлый выбор, сделанный в обозревателе, не должен перетираться лендингом.

## 4. Влияние

| Область | Влияние |
| --- | --- |
| Шаблоны / SCSS | Нет. Механизм темы не меняется — middleware лишь пишет тот же cookie, который уже читают `commonData` и `theme_service.js` |
| JS | `theme_service.js`: `darkEnabled()` переведён с «наличия cookie» на **значение** (`=== '1'`), переключатель-солнце при светлой теме пишет `=0` вместо удаления cookie. Клиенты темы (`tx_controller`, `chart_panel`, `agendas_controller`, `attackcost_controller`) не меняются — они используют `darkEnabled()` |
| `MenuFormParser` | Переведён на значение: светлая тема пишет `=0` (а не удаляет cookie), тёмная — `=1` |
| API | Не затрагивается (middleware живёт на web-группе) |
| ETag-кэш | Не меняется; порядок middleware гарантирует, что cookie доставляется и при 304 (§3) |

## 5. Известные ограничения

- Cookie выставляется только при первом заходе с параметром. Если посетитель сначала открыл обозреватель напрямую (cookie создана), параметр лендинга больше не подействует — это намеренно (выбор в обозревателе приоритетен).
- Тема из лендинга не «следит» за последним выбором на лендинге: она применяется один раз при отсутствии cookie. Изменение темы на лендинге при уже существующей cookie обозревателя игнорируется.
- `?theme=` остаётся в URL после применения (редиректа на чистый URL нет). Повторный визит по той же ссылке безвреден: cookie уже есть, параметр игнорируется.
- Cookie **значением** (`=1`/`=0`) — обратная совместимость с прежней схемой «наличие = тёмная»: существующие тёмные cookie были `=1` и остаются тёмными; существующие светлые (без cookie) остаются светлыми. Новых пользователей с `=0` раньше не было, поэтому перехода не требуется.

## 6. Тесты

`TestThemeFromQueryParser` в `cmd/dcrdata/internal/explorer/explorermiddleware_test.go`:

1. `dark` без cookie → в ответе `Set-Cookie: monetariumDarkBG=1`, cookie видна текущему запросу (`r.Cookie`), обработчик вызван.
2. `light` без cookie → `Set-Cookie: monetariumDarkBG=0`, запросу cookie со значением `0` видна.
3. Без параметра → ничего не происходит.
4. Неизвестное значение (`neon`) → ничего не происходит.
5. `?theme=light` при существующей тёмной cookie (`=1`) → не перетирается.
6. `?theme=dark` при существующей тёмной cookie (`=1`) → не перетирается (шаг 1).
7. `?theme=dark` при существующей светлой cookie (`=0`) → светлая сохраняется, не перетирается.

`public/js/services/theme_service.test.js`:

1. `darkEnabled()` — `true` при `=1`, `false` при `=0` и без cookie.
2. `toggleSun()` со светлой темы пишет `=1`; с тёмной (cookie `=1`) пишет `=0`, а не удаляет cookie.

`TestMenuFormParser` (`explorermiddleware_test.go`): форма `POST /set` по-прежнему отвечает 302-редиректом на указанный путь.
